## B. 매출현황 '실제 송장(합배송 반영)' 보조 표시 (PR #316)
- 배경: 주문건수 2,747 vs 택배출고 2,746 문의 → 데이터로 규명: 차이 1건 = 과거·도매 1건 제외분. 같은 주문번호 합구매는 그날 0건.
- 핵심: 기존 '택배 출고'는 **주문번호 기준**이라, 서로 다른 주문번호를 한 박스로 묶는 **합배송(같은 수취인+주소 → 송장 1장)** 이 반영 안 됨.
- 구현: 택배출고 카드 아래 **"실제 송장 N건 (합배송 반영)"** 보조 표시. 같은 날·사업자·수취인·주소 = 1송장, 주소 없으면 주문번호 폴백(courier_count 수동값 반영). 필터(취소·과거·도매·직접수령·화물 제외)는 기존과 동일. orders 조회에 recipient_name·address 추가.
- 기존 '택배 출고' 정의는 변경하지 않음(보조 표시만 추가 — 사용자 선택).

## C. 실운임(건당 2,300원) 정책 결정 — 보수적 유지
- 현행: 공헌이익의 실운임은 **주문번호당 1회** 차감. 합배송이면 실제 택배비(송장당)보다 과다 차감 = 공헌이익이 보수적으로 계산됨.
- 측정(8/1~8/18): 주문번호 8,101 vs 실제송장 7,983 → 합배송 118건, **과다계상 271,400원** (공헌이익 대비 1% 미만).
- **결정(사용자)**: 오차가 미미하므로 **현행 유지**. 전환 기준: 과다계상이 **월 100만 원대**를 넘으면 실송장 기준으로 변경(공용 함수 `computeOrderLines` 한 곳 수정 → 매출현황·주문조회·슬랙봇 동시 반영).
- 진단 SQL 주의: `source not in ('과거','도매')`는 NULL(일반 주문)을 탈락시킴 → 반드시 `coalesce(source,'')`로.
